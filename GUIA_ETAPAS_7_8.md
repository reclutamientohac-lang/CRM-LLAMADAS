## Activación

Instala las dependencias con `npm ci`. Usa `npm run dev` para desarrollo y `npm run build` para producción. Verifica el proyecto y la base de datos antes de publicar reglas o conectar datos reales. La configuración incluida sigue apuntando a la base con nombre `ai-studio-e3fb58d5-7744-4050-bf57-8e9490a79402`, del proyecto exportado. No se sustituyó por otra base ni se migraron datos.

Para desplegar reglas sobre ESA base, utiliza `firebase.named.json`, después de comprobar el proyecto en la consola: `firebase deploy --project project-76706253-7b54-4622-a4a --config firebase.named.json --only firestore`. Para un Firebase propio en Spark, configura `firebase-applet-config.json` con los valores de tu proyecto y la base `(default)`, verifica el acceso Google y utiliza `firebase.json` para publicar reglas e índices. Cambiar el nombre de la base no migra los datos: consulta primero la base original y conserva un respaldo. La acción de publicación no se ha ejecutado en esta entrega.

Firebase indica que las bases con nombre no tienen cuota gratuita y requieren facturación. La cuota gratuita de Firestore se aplica a una base por proyecto; no es posible garantizar Spark conservando una conexión a una base con nombre. Referencia oficial: https://firebase.google.com/docs/firestore/pricing . ## Reportes y cálculos

Las definiciones viven en `src/businessRules.ts`; el cálculo se ejecuta en un Web Worker. Los datos ya cargados por el contexto del CRM se reutilizan durante la sesión, por lo que cambiar de reporte no genera una nueva consulta de datos de actividad. Los módulos previos mantienen sus suscripciones generales para administrador y supervisor; esta entrega no reemplaza su modelo de carga inicial. Una primera carga de una base muy grande puede alcanzar la cuota diaria gratuita, aunque el cálculo local sea rápido.

Actividad cuenta eventos ocurridos dentro del período. Prospectos cuenta las recepciones o prospecciones del período cuando se elige una de esas bases; las llamadas, citas y ventas del período pueden corresponder a prospectos recibidos antes. En consecuencia, el cociente contactados/prospectos puede superar el 100% en Actividad; no debe interpretarse como conversión de una misma cohorte. Cohorte toma los prospectos recibidos en el período y todo su historial posterior. Cuando se usa una base de evento en Actividad, se limita la población a prospectos con ese evento dentro del rango. En agrupaciones por fecha, el prospecto se cuenta una vez en la primera fecha de ese evento durante el rango; los eventos se agrupan por su fecha base disponible y, cuando no la tienen, por la primera fecha base del prospecto. Las fechas se interpretan en America/Los_Angeles.

Las gestiones, citas y ventas heredan propietario, tipo, origen, ciudad y telemarketing actual del prospecto. “Contactados” cuenta IDs de prospecto únicos con al menos una gestión. Contactos cuenta gestiones y efectivos cuenta gestiones con efectivo “Sí”. Citas agendadas cuenta registros de cita, incluidas las canceladas; realizadas cuenta estado “Realizada”. Pendientes de resultado cuenta citas no canceladas sin retroalimentación registrada, incluidas citas futuras. Ventas cuenta ventas no canceladas. Monto suma únicamente ventas aprobadas; bonos suman las ventas no canceladas y usan los importes ya calculados por los módulos anteriores. Ninguna comisión se recalcula al consultar reportes.

Los porcentajes usan los cocientes solicitados: contactados/prospectos, efectivos/contactos, citas/efectivos y ventas/citas. Se muestran con un decimal y son cero si el divisor es cero. Los totales recalculan cocientes; no suman porcentajes. Los propietarios se agrupan sin mayúsculas, tildes ni espacios repetidos. Unificar propietarios modifica nombres guardados únicamente después de una confirmación escrita y otra confirmación del resumen; registra nombres anteriores, nombre final y cantidad aplicada en auditoría.

Por propietario, fecha, telemarketing, tipo, origen, ciudad, estado, temperatura, citas, ventas y bonos, embudo y cruces tienen filtros comunes. Constructor permite hasta dos dimensiones; la matriz muestra la medida seleccionada y totales por fila y columna, además de la tabla completa de medidas. Las tablas tienen totales, búsqueda, orden y páginas de 50 filas. Los porcentajes abren detalles con sus componentes de numerador y denominador.

Excel incluye Resumen, Detalle y Filtros; los cruces y el Constructor también incluyen Matriz. CSV utiliza UTF-8 con BOM y protege las celdas de texto que podrían interpretarse como fórmulas. Imprimir/PDF abre una vista limpia con advertencia de datos personales. La exportación de todos los reportes reúne las agrupaciones predefinidas con los filtros actuales; incluye el cruce predefinido de propietario por telemarketing. Los gráficos se construyen con Recharts.

## Respaldo

El JSON oficial incluye app, versión, usuario, fechas de lectura, IDs de documentos y todos los campos permitidos. Los Timestamp se representan como ISO junto con metadatos que conservan los nanosegundos para restauración. También se conservan GeoPoint, referencias y bytes mediante metadatos de tipos. Las fechas que originalmente son texto conservan su valor literal; no se altera una fecha local para convertirla artificialmente en un instante UTC. Excel presenta fechas legibles y teléfonos como texto.

El hash SHA-256 se calcula sobre el JSON canónico sin el campo hash: se ordenan las claves de objetos y se conserva el orden de las listas. El hash está dentro del archivo y en la ficha de respaldo. Detecta daños o modificaciones accidentales; no es una firma que certifique al emisor. El Excel no es un archivo de restauración. ZIP contiene el JSON oficial y el Excel.

Se leen páginas de 500 documentos. Los puntos de reanudación se conservan por usuario en IndexedDB del mismo navegador. Si se agota la cuota, no se ofrece una descarga incompleta como respaldo completo; se puede continuar en otra jornada marcando Reanudar. El administrador puede eliminar el punto temporal. No hay Cloud Functions, Cloud Storage, tareas de servidor ni servicios de pago implementados.

No existe una API del SDK web para descubrir colecciones arbitrarias o subcolecciones. La aplicación verifica las colecciones conocidas del proyecto, incluidas configuraciones y auditorías, y amplía esa lista desde `settings/backupRegistry`. Una nueva colección externa debe registrarse mediante la sección Registro de colecciones. Las nuevas colecciones registradas quedan accesibles solo para el administrador bajo las reglas incluidas. No se incluyen datos de Firebase Authentication, credenciales ni tokens. Si aparece un campo de autenticación dentro de documentos, se detiene el respaldo y se explica la causa, evitando borrar silenciosamente ese campo. Referencia oficial: https://firebase.google.com/docs/firestore/query-data/get-data .

Spark tiene límites diarios de 50.000 lecturas, 20.000 escrituras y 20.000 eliminaciones. Paginar no reduce esas cifras. 30.000 prospectos y 100.000 gestiones no pueden leerse por completo en una sola jornada gratuita. Las consultas del CRM también consumen cuota. Una lectura reanudada de varios días no es una instantánea atómica de toda la base: cada página representa su momento de lectura. El JSON registra inicio y fin. Para obtener un estado coherente, realiza respaldos y restauraciones durante una pausa de uso y evita cambios mientras se lee. Referencia oficial: https://firebase.google.com/docs/firestore/quotas .

Las alertas de último respaldo solo cuentan respaldos completos oficiales; no cuentan Excel de consulta ni copias de seguridad previas a restauración. El historial muestra inicialmente las cien fichas más recientes y permite cargar las anteriores. Los archivos se guardan en el equipo del administrador. Cuando el navegador soporta el selector de archivos, se espera al cierre correcto del archivo. En navegadores que usan la descarga tradicional no existe una API fiable para verificar que el archivo terminó de descargarse; la restauración exige que el administrador verifique y confirme expresamente que el JSON de seguridad está guardado.

## Restauración

El JSON se valida antes de leer la base para vista previa: identidad de la app, versión, fecha, estructura, colecciones registradas, IDs únicos, metadatos de tipos, ausencia de credenciales y hash si existe. La vista previa compara nuevos, diferentes y registros solo en la base. Elegir una colección nunca implica borrar automáticamente lo que solo existe en la base.

Recuperar faltantes crea solo IDs ausentes. Reemplazar sobrescribe los documentos del archivo y conserva otros documentos, salvo eliminación explícita con confirmación adicional. UsuariosAutorizados queda excluida por defecto; la cuenta administradora no se restaura ni se elimina. Las auditorías, fichas de respaldo y logs de restauración se preservan y no se reescriben desde un archivo anterior. Se descarga antes una copia completa de seguridad y se exige revisar el resumen y escribir RESTAURAR; eliminar exige además ELIMINAR.

Los lotes usan transacciones de hasta 200 operaciones de datos más una escritura del progreso. Se limita también el tamaño aproximado por lote. Cada lote compara la versión actual con la vista previa para no sobrescribir cambios simultáneos ni crear un ID que apareció después. Los padres se crean antes de sus dependientes y se eliminan después. Una selección parcial que introduzca registros sin prospecto o sin cita se rechaza. No se permite eliminar padres dejando hijos existentes.

No existe una transacción global ni un rollback automático para toda la base. Al cancelar o fallar, se conservan los lotes confirmados y se indica el número de lote, operaciones aplicadas y pendientes. El progreso de cada lote se escribe de forma atómica junto con sus datos en logRestauraciones. Para continuar, carga de nuevo el archivo, actualiza la vista previa y genera otra copia de seguridad; en modo faltantes, lo ya recuperado se conserva. La restauración puede agotar las cuotas diarias y requerir varias jornadas.

La papelera conserva prospectos archivados y permite recuperarlos. La eliminación definitiva exige dos confirmaciones y se bloquea si quedan gestiones, citas, resultados o ventas asociadas. Las fechas, autor y motivo de archivos antiguos solo pueden mostrarse si ya fueron registrados. Desde esta actualización se guardan fecha y autor de archivo y se conserva la observación como motivo.

## Consulta Global e integridad

La búsqueda normaliza teléfonos y reconoce nombre, propietario e IDs de prospecto, cita y venta. Los resultados están agrupados y abren el expediente: datos, gestiones, citas, resultados, ventas y bonos, cambios de venta, lote y cambios de asignación. Se exporta a Excel o impresión/PDF. Los cambios anteriores de asignación no se inventan; se registran desde esta actualización.

Revisar datos consulta las colecciones completas con lectura paginada para encontrar registros huérfanos aunque no estén cargados en una pantalla. Informa gestiones/citas sin prospecto, ventas sin cita, teléfonos duplicados, telemarketing inexistente, fechas inválidas, sin asignar por más de siete días y ventas aprobadas sin monto/porcentaje. No modifica nada. Los registros válidos enlazan al prospecto; un huérfano abre una vista de solo lectura del registro, con su ID y colección, porque no hay un prospecto existente que abrir. Se exporta el informe a Excel.

Firebase Tools 14 requiere Java 17 o superior para estas pruebas; si actualizas la herramienta, revisa sus requisitos de Java.

La validación no sustituye una prueba de acceso Google y despliegue en tu proyecto real: no se consumieron tus credenciales ni se publicaron reglas automáticamente.
