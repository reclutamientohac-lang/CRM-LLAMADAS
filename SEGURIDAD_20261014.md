# Correcciones de seguridad — 14 de octubre de 2026

Telemarketing registra resultados de citas y reporta una venta pendiente, sin monto, porcentaje ni bono. Esta restricción se aplica en Firestore a todos los roles excepto el administrador. Solo el administrador modifica importes, porcentajes, aprobación, pagos y reglas de comisión. Las cuentas de Supervisor de la versión original conservan su trabajo operativo; no tienen aprobación financiera. La versión personal no habilita Supervisor.

Los nuevos cálculos financieros usan centavos enteros y puntos básicos del porcentaje. Se descartan las cifras sobrantes hacia cero: 123.459 pasa a 123.45; un bono de 1.519 pasa a 1.51. Se muestran importes con dos decimales. No se recalculan automáticamente ventas ni bonos históricos. Una edición financiera explícita sí aplica el nuevo cálculo. Las nuevas ediciones se verifican con reglas y una bitácora atómica con fecha de servidor. El historial antiguo no adquiere validez retrospectiva por esta corrección. Las auditorías generales son declaraciones del cliente con actor y hora verificados, no prueba independiente de cada acción; los logs financieros se vinculan a la escritura de la venta. Un propietario de infraestructura con Admin SDK puede saltarse reglas: esto no equivale a un archivo probatorio inmutable externo.

Las llamadas se registran en transacción, con incremento atómico y un identificador estable para reintentos del formulario. Los nuevos IDs usan UUID. El resultado de venta se guarda en transacción y usa un ID estable por cita para nuevas ventas, conservando las existentes. El borrado global de muestras está deshabilitado y retirado de Configuración. Se eliminan las escrituras automáticas de temperatura al iniciar; la temperatura sigue calculándose al leer. Las importaciones Excel aceptan hasta 5 MB y 5000 filas, con SheetJS 0.20.3 y lock npm incluido. CI usa npm ci.

## Activación coordinada, sin modificar históricos automáticamente

Conservar un respaldo completo antes de publicar. Ejecutar npm ci y npm run verify:release. Revisar visor y roles antes de publicar aplicación y reglas en el proyecto y base correspondientes a ESTA versión. No intercambiar Firebase, administrador ni Calendar entre versiones. Estas modificaciones del repositorio no publican Firebase ni AI Studio.

Las nuevas altas y cambios de teléfono requieren un índice único preparado. Con la aplicación y reglas actualizadas, entrar como administrador a Configuración > Protección de teléfonos duplicados > Verificar sin modificar. Resolver manualmente duplicados o teléfonos inválidos, conservando historiales y bonos. Solo entonces usar Preparar índice. Este proceso añade documentos telefonosUnicos y settings/phoneIndexStatus; no fusiona ni borra contactos. Hasta completarlo las altas fallan con un mensaje claro. Coordinar una ventana sin altas ni restauraciones. Después de restaurar prospectos se invalida el índice: volver a verificar y preparar. La recuperación de conflictos de índice tras eliminar o restaurar contactos requiere revisión; no limpiar reservas automáticamente porque puede permitir duplicados. No ejecutar importaciones administrativas históricas o cargas de demostración sin volver a verificar el índice. No mezclar clientes antiguos y nuevos durante la activación.

## Trabajo adicional pendiente

La escucha de colecciones completas y la segmentación por ocho prospectos todavía requieren rediseño con paginación y agregaciones para carteras grandes; retirar escrituras de temperatura no resuelve toda la escalabilidad. App Check y recuperación administrativa requieren configuración y pruebas en las consolas de cada proyecto. Las reglas no constituyen un esquema exhaustivo de todos los campos de todos los módulos. Aún se necesita una revisión de interfaz autenticada, volumen remoto real y reglas efectivamente publicadas. Los respaldos administrativos conservan capacidad de restaurar documentos históricos con esquema antiguo. No se desplegó un backend financiero separado ni se migraron masivamente montos históricos.

Las ediciones financieras se guardan en grupos de hasta cinco ventas para respetar el límite de consultas de reglas de Firestore. La restauración conserva las entradas financieras existentes; añade las históricas faltantes con marca de importación y fecha de servidor, sin convertirlas en evidencia original. Restaurar una venta existente crea una entrada nueva del cambio administrativo. El borrado de ventas queda bloqueado: se cancelan para conservar el historial.


## Corrección de lectura previa de IDs nuevos

Las transacciones de registrar llamadas, crear citas y reportar ventas consultan el ID candidato antes de escribir, para evitar sobrescrituras y reconocer reintentos. Las reglas basadas solo en resource.data rechazaban esa consulta cuando el documento aún no existía, incluso para una telemarketing autorizada. Se permite únicamente get de documentos inexistentes en gestiones, citas y ventas a usuarios autorizados. Los documentos existentes conservan los límites por cartera; list y todos los permisos de escritura permanecen iguales. Una prueba ejecuta la transacción de llamada con contador atómico y verifica que carteras ajenas, consultas globales de telemarketing y cuentas sin sesión sigan bloqueadas. Publicar el firestore.rules de cada repositorio en su propia base para activar esta corrección; guardar código en GitHub no publica reglas.
